# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

MCP server that converts heavy Cocos Creator `.scene` files (~700KB JSON) into compact semantic scene graphs (~20KB) for AI coding assistants, and edits scenes/prefabs through semantic operations. Twenty-two MCP tools: scene reading (`query_scene_graph`, `query_prefab_graph`, `query_animgraph`, `query_terrain` — in-depth read of a `.terrain` binary incl. height/weight sampling plus the `contourAt`/`slope` readouts a blend edit is designed and verified with, `list_scene_scripts`, `find_scene_nodes` — by name pattern, component and/or world-XZ region, `inspect_node`), project/asset introspection (`get_project_info` — incl. a resolved-project-root self-check, `get_asset_info`, `list_assets`, `find_asset_references` — reverse "who uses this asset/UUID" lookup), writing (`apply_edits`, `validate_document`, `build_prefab`, `build_animgraph`, `build_terrain`, `edit_terrain` — eight semantic ops over an existing `.terrain`, `create_asset_meta` — offline `.meta` generation so assets created outside the editor are importable with a stable UUID), and measurement/hygiene (`get_node_bounds` — incl. `perChild` world AABBs, `compute_fit_scale`, `compute_rotation`, `lint_assets`).

Locked decisions (details and verified Cocos 3.x format notes live in [README.md](README.md)): LLMs never text-edit `.scene`/`.prefab`/`.terrain` files — only semantic operations (a `.terrain` is a raw binary, so "text-edit" is not even an option: `build_terrain`/`edit_terrain` own the bytes); nodes are addressed by path or stable `_id`, never by `__id__`; edit the source prefab, not the instance (instance internals exist only as overrides); wrapper convention — a model/sprite is never the prefab root (`Root` → `Visual` child). A companion Claude Code SKILL `cocos-scene-builder` (policy/recipes on top of these tools) is distributed outside this repo.

## Architecture

ES modules (`"type": "module"`), plain JavaScript, Node >= 18, single dependency (`@modelcontextprotocol/sdk`).

### Data Flow

```
.scene JSON → SceneParser (index) → NodeTreeBuilder (tree) → Formatter (output)
                                       ↑           ↑
                                  TypeFilter    ScriptResolver
                                  NodeFilter    PropertyExtractor
```

**SceneParser** reads the flat JSON array from a `.scene` file and indexes objects into nodes (`cc.Node`/`cc.Scene`) and components maps. **ScriptResolver** scans `assets/**/*.{ts,js}.meta` files and maps compressed component UUIDs to script names by exact compression (`src/utils/uuid.js`). **NodeTreeBuilder** recursively builds a minified tree — including a node's TRANSFORM wherever it is non-default (`pos`, `scale`, `euler`; euler derived through math3d's verified `quatToEulerYZX` when only `_lrot` is stored), near the top of the tree by default and at EVERY depth under `transforms: 'all'`, which `SceneMinifier.inspectNode` passes: a tool whose stated purpose is full unfiltered detail for one node must not hide its transform, and before this the only way to read a scale was to (dry-)run a write, since `MiniTree` — the apply_edits RESPONSE renderer — was the only place that printed one. A collapsed instance stub has no transform FIELDS: its placement is a `CCPropertyOverrideInfo` on the source root, so `SceneParser.getInstanceInfo` returns that root's single-segment `overrides` map (`_lpos`/`_lrot`/`_euler`/`_lscale` alongside the `_name` it already read) and the builder prefers it over the node — otherwise every instance of a scene printed at its parent's origin, which is precisely the placement the transform was added to answer (68 stubs in the golden scene, not one with an `_lpos` of its own). It uses **TypeFilter** to skip noise types (transforms, UI renderers), **NodeFilter** to skip skeleton bones, and **PropertyExtractor** to pull meaningful props from custom script components (and built-in `cc.*` in detailed mode); asset references — including `_materials` arrays — resolve to names via `AssetIndex.label()`: sub-assets as `file@subId`, fbx-baked materials marked `(embedded)`, engine built-ins as `builtin:<name>`. Formatters (Text/Json/Stats) render the final output.

**SceneMinifier** is the facade/orchestrator that wires all core classes together via constructor injection.

### Asset Layer

**AssetIndex** scans `assets/**/*.meta` and resolves any reference form — project-relative path, full UUID, compressed UUID, or `<uuid>@<subId>` sub-asset — plus filtered listing (type/folder/pattern; `TYPE_ALIASES` covers `terrain` too, so it is a documented knownType even in a project with no terrain). `ListAssets` chooses the output SHAPE per question, because the wrong one costs an order of magnitude: `grouped` (default — folder hoisted into a header, type hoisted when uniform), `summary` (counts per type and per folder, no enumeration: the "what is in this project" question cost 8 316 tokens as a 210-row listing against 210 as counts, measured; the per-type and per-folder ranks are capped at 24 / 16 buckets and state the count of the ones they left out — `, ... N more` — because a shape sold as the whole inventory must not sum to less than its own header, and a count rather than a second enumeration is what keeps that win), `flat`/`text` (the pre-grouped one-row-per-path shape, and an explicit `flat` call still carries the full uuid so old callers are unaffected) and the untouched `json`. Matches are ordered by (folder, then name — never by the full path, which sorts a subfolder's rows between its parent's and splits the header) once for EVERY shape, `json` included, and BEFORE the `MAX_RESULTS` slice so truncation is deterministic: `AssetIndex` scans depth-first and never sorts, so a folder holding files both before and after a subdirectory opened two identical grouped headers with disjoint contents (36 headers for 34 folders on zombie-miner, measured). The uuid is opt-in (`uuid: "none"|"compressed"|"full"`, defaulting PER FORMAT and therefore carrying no schema `default` at all — `grouped` `none`, an explicit `flat`/`text` `full` so a pre-2.0 call keeps its uuid, `json` always full, `summary` has no rows) because `resolve()` accepts a project-relative path anywhere a uuid works, while a full uuid is ~25 o200k tokens against ~5 for the path it sits beside; the omission is stated in a one-line footer so the capability stays discoverable. `#renderSummary` buckets by DIRECTORY, never by path segments — a root-level asset would otherwise contribute its own file name as a folder. **builtins.js** resolves UUIDs of the editor's internal db (`db://internal`: primitives, default materials/effects/spriteFrames/fonts) against the static table `src/assets-data/builtins-3.8.json` (407 assets, harvested from an installed Cocos Creator 3.8.7 by `scripts/harvest-builtins.mjs`): `AssetIndex.label()` falls back to `builtin:<name>`, `get_asset_info` answers with an "engine built-in" card, and the validator's missing-asset warning excludes known builtins (only genuinely unknown UUIDs are reported). **FindAssetReferences** is the reverse lookup: a string scan over `assets/**` serialized files, then a deep pass over matching scenes/prefabs attributing every `__uuid__` hit to `node path ▸ component.property` (hits inside standalone value objects climb to their owner through a reverse-reference map); `.mtl`/`.anim`/`.animgraph` files report at file level, and `.terrain` gets a third, STRUCTURAL bucket (`BINARY_EXTENSIONS`): a layer's detail/normal map is a plain ASCII `<uuid>@<subId>` string inside the binary, so `readTerrainLayout` parses the layer table — the palette sits behind the payload arrays, walked but never copied — and every hit is attributed as `terrain layer N .detailMap` — the branch runs BEFORE the utf-8 read and its substring pre-filter, is skipped entirely for script targets (a binary cannot hold a `__type__`), and folds into the same totals. A utf-8 `includes()` would in fact match those bytes; the point of the branch is attribution instead of a bare count, and not decoding 100+ KB of heights/weights as text. **AssetInspector** extracts per-type details: sprite rect/trim/9-slice from meta subMetas, mesh AABB from compiled `library/<xx>/<uuid>@<subId>.json` (fallback: glTF POSITION accessors for `.glb`), prefab summaries, material effect/defines, and a terrain card (`readTerrainInfo` + layer textures resolved through `AssetIndex.label()`, memoized per path + nanosecond mtime + size because pow-2 padding makes a rewritten terrain the same length; the card emits both the flat `heightMin`/… keys and the nested `height: {}` block `query_terrain` uses, so one consumer code path reads either tool). **ProjectInfoReader** reads engine version (`package.json` → `creator.version`), designResolution/layers/physics (`settings/v2/packages/`); `get_project_info` renders it plus a one-shot self-check of the RESOLVED root (`assets/`/`library/` present, assets indexed), because a root mismatch fails asymmetrically — the `assets/`-scoped writers refuse loudly while the read tools degrade quietly (raw UUIDs, every mesh AABB "unavailable", phantom broken-reference warnings), and diagnosing that otherwise costs several tool calls. `src/utils/uuid.js` implements the verified Cocos UUID compression algorithm (5 hex chars kept + 3-hex→2-base64 packing) and `nameToId` — subMeta ids are 5 chars sampled from the md5 of the sub-asset name (ported from npm `@cocos/asset-db`, verified: `texture`→`6c48a`, `spriteFrame`→`f9941`); `src/utils/glb.js` reads GLB JSON chunks, `src/utils/terrainBin.js` the `.terrain` native binary and `src/utils/heightmap.js` heightmap sources (see Terrain Layer).

### Write Layer

`src/document/` is the lossless counterpart to the lossy read pipeline. **SceneDocument** loads the flat JSON array, addresses nodes by path (`Canvas/Panel/BuyBtn`, `Name[i]` disambiguation) or scene `_id`, and saves atomically (temp+rename). Canonical form — verified byte-identical with editor output on the golden corpus — is depth-first first-visit numbering over the whole reference graph plus `JSON.stringify(arr, null, 2)` with no trailing newline; `renumber()` restores it and garbage-collects unreachable objects. **operations.js** implements the fifteen semantic ops (all-or-nothing batches) — terrain DATA ops are deliberately not among them (a `.terrain` is a binary asset with its own eight-op table in `terrainOps.js`), so this count stays fifteen; property paths navigate THROUGH `{__id__}` refs to standalone value objects (`cc.Line` `width.constant` edits the referenced `cc.CurveRange`; object values merge through the ref, primitive writes are rejected with a hint). **typedValues.js** owns what a written VALUE has to look like, because Cocos rebuilds one from the `__type__` tag next to it and both halves of that were silently wrong: (1) `mergeTyped` carries the tag over from the value it merges INTO, so the merge form `{width: 184, height: 184}` only kept it where the file already had one — a `null` field, or ANY field of the script component `build_prefab` has just created (`createScriptComponent` emits no user fields at all), had nothing to inherit and was written untagged, which deserializes as a plain object and leaves the component on its DEFAULT (`Size(0, 0)`, `Color(0, 0, 0, 255)`, an empty array) while every structural invariant still holds and `validate_document` says 0 errors — silent on both sides, so such a write is now REFUSED (`isUntypedObjectWrite`/`untypedValueError`, naming the value types whose field set fits the keys), as is an array or scalar written OVER a typed value (`_contentSize: [184, 184]` — the same default, one spelling further out) while `null` still clears a field, and `{"$plain": {…}}` (a WeakSet brand set by the `$plain` sentinel in transformValue, unforgeable by file content) marks the rare field that genuinely is an untyped dictionary; (2) a custom `@ccclass` value is a STANDALONE object of the flat array with an `{__id__}` reference from its owner — `cc.ClickEvent` proves it in an editor-saved file (`test/fixtures/real-prefabs/Toilets.prefab`: `CocosEvent._handlers` holds refs, never inline objects) — and only `VALUE_TYPE_FIELDS` types stay inline, so `materializeTypedValue` hoists every tagged non-value object at EVERY depth (`moveAnim` → `AnimationSet` → `DirectionFrames[]`), shared by `set_component_property`, `add_component`/`build_prefab` properties, `insert_array_element`'s `value` fields (`materializeTypedFields` — there the root is a bag of fields, not a value) and instance overrides, which is why `buildElementFromType`'s one-level hoisting is no longer the only place that knows the rule; a `__type__` naming a node/scene/plumbing record is refused rather than minted. `normalizeNodeProperty` supplies a TYPED zero/one base for position/rotation/scale, since a node storing only `_lrot` (no `_euler`) and a first-time instance override both used to merge onto `undefined` and produce an untyped `{y: 90}`. The validator's `#checkTypedValues` finds files written before this: a `cc.*` field holding an untyped object or an array where the 3.8.7 template declares a typed value (templates are a registry, not a guess — a script's field types live in its `.ts` and are unknowable here, so only `cc.*` is checked, and the golden corpus stays clean). Top-level property spellings get one underscore-tolerance retry (`sizeX` → `_sizeX`, and therefore `_asset` → `__asset` for free) plus a per-type `PROPERTY_ALIASES` map for what that retry cannot reach — currently the single entry `cc.Terrain` `asset` → `__asset` (the `@serializable` member really is `protected __asset`; `_asset` is only a facade), applied only when the aliased key exists on THIS object so a stale template never gets a manufactured field. Every one of those existence tests is `Object.hasOwn`, never `in` (the same hardening the `HANDLERS` op lookup already carries): `toString`/`constructor`/`valueOf`/`hasOwnProperty` resolve through `Object.prototype`, so `in` accepted them as fields that already exist and `set_component_property {property: "toString"}` wrote a `"toString": 42` own key into the `.scene` that `validate_document` does not flag. `resolveTopSegment` is exported because `locateProperty` is not the only resolver: `overridePathForComponent` in instances.js no longer builds instance-override `propertyPath`s independently — it CALLS it, since the engine applies an override with a bare `targetPropOwner[name] = value`, so an unrecognized path is not an error but a silently dead override, and a WRITE naming a property the source component does not have is now rejected instead of serialized (a single-segment write on a user SCRIPT component still creates: its fields live in no registry and the engine fills declared defaults). REMOVAL is deliberately lax the other way — `removalPathsForComponent` tries the path AS STORED plus the write form and the underscore twin — because a stale record naming a property the source lost must stay removable, and there is no `prune_dangling_overrides` for property overrides: a strict resolver on the cleanup path made the tool refuse to clean up the very mess the lax one used to create. `IMPORTER_TO_TYPE` maps `terrain` → `cc.TerrainAsset`, serving both `cc.Terrain.__asset` and `cc.TerrainCollider._terrain`. `set_component_property` only edits the FIELDS of an existing element of a `CCClass[]` property (a `{__id__}`-ref array like `CardsBase.entries: CardEntry[]`) — changing the SET of elements is `insert_array_element`/`remove_array_element`: insert deep-clones a neighbor element as the skeleton (that is where the full field set comes from — user CCClasses have no default registry; `cloneOwnedElement` allocates FRESH owned sub-objects so `config`/`members` never alias the source), merges `value` over the top-level fields, and splices in the new `{__id__}`; remove splices the element out and, for a reference to an OWNED value object, GCs its subtree on renumber with the same reachability guard as `remove_node`/`remove_component` — a reference to a live node/component (`pipeControllers: Foo[]`) is just a dropped link, the target stays. Ownership is decided by `_components`/`MountedComponentsInfo` MEMBERSHIP (`collectComponentIndices` in the shared `src/core/componentIndices.js` registry — single source for read recursion and write ownership/GC, behind `componentIdxSet`/`isValueObjectIdx` in operations.js and PropertyExtractor's struct check; it also owns `INTERNAL_STRUCT_TYPES`, the engine plumbing types that LOOK like data structs — `cc.PrefabInfo`/`cc.PrefabInstance`/`cc.CompPrefabInfo`, `cc.TargetInfo`/`cc.TargetOverrideInfo`, `CCPropertyOverrideInfo`, both Mounted*Info records — which the reader must not recurse into and the writer must not treat as owned value objects), never by the `node` back-ref heuristic — a user data struct with a `@property node: cc.Node` field is still an owned struct. Both splice ops remap `cc.TargetOverrideInfo.propertyPath` index segments running through the array (drop for the removed element, ±1 for shifted ones — `remapTargetOverridesForSplice`), and insert additionally DUPLICATES the cloned neighbor's live overrides onto the new index (`elementTargetOverrides`): the clone copies the neighbor's serialized `null` but not the record that fills it in, so without the duplicate the "cloned" reference is dead — records `overrideDeadReasons` already calls dead are not carried along, and a field `value` merges over keeps its own value instead. Insert rejects a `from` pointing at a null hole (nothing to clone; an explicit reference value is still accepted). A `guardTypedRefArrayWrite` footgun check rejects a bare-value write into the append slot / a null hole of such a ref-array (which would otherwise serialize an inline object where the engine expects a `{__id__}` — silent corruption), pointing at `insert_array_element`; writing `null` is allowed (null holes are a legal serialization present in the golden corpus). Inline value-type arrays (`cc.Vec2[]`, any type in the shared `src/core/valueTypes.js` registry — single source for read rendering and write membership, incl. `cc.Mat4`) and scalar arrays are supported too. `prune_dangling_overrides` tidies editor-left dead `cc.TargetOverrideInfo` records (null/detached/invalid endpoints the engine skips on load; editor forms like `target: null` are never flagged). These dead records are NON-blocking: the validator reports each as a single warning (they cannot affect the runtime, and the editor regenerates some — e.g. a half-written `source: null` skeleton — on every save, so erroring would create an MCP↔editor whack-a-mole), so `apply_edits` proceeds without a prune call; the op stays available as opt-in cleanup and `validate_document` hints at it whenever such records exist. `overrideDeadReasons` (exported from targetOverrides.js) is the single source of truth for "engine skips this on load" — shared by the validator and prune, it subsumes the old structural error branches, so only sourceInfo↔source consistency on a LIVE record is still a hard error; `deadOverrideShellNodes` (same module, same predicate) is what keeps that decision from being undone through a second code path: the editor leaves behind `cc.Node` SHELLS — nothing but `__type__`/`__editorExtras__`, unreachable from the hierarchy, referenced only by such a dead record — when a component referencing INTO a prefab instance is deleted, and the scene-wide "every `cc.Node` has an `_id`" rule was erroring on them, making a scene that opens and runs fine unwritable by `apply_edits`. The exemption is narrow by construction: any own key beyond those two, any attachment to the tree, or any OTHER incoming reference (checked through `externalRefsInto`) makes it a real node again and the missing `_id` a genuine error; `add_component` auto-adds missing companions BEFORE the component itself, mirroring the editor (adding `cc.Sprite`/`cc.Widget`/… inserts `cc.UITransform` first; `cc.SafeArea` pulls in `cc.Widget`→`cc.UITransform`; `cc.LabelOutline` pulls in `cc.Label`) — idempotent, so it never adds a second `cc.UITransform` to a node that already has one; the forward map `COMPANIONS_FOR` is derived from `REQUIRED_COMPANIONS`, and `attachCreatedComponent`/`ensureCompanions` share the template-instantiation path. Without this a UI node lacking `cc.UITransform` serialized as "valid" but crashed the editor on scene activation (`Widget.onEnable`/`align` read a null UITransform). `remove_component` mirrors `remove_node` (detach → reachability-filtered external-ref check → GC on renumber) with a `REQUIRED_COMPANIONS` guard (`cc.UITransform` is not removable while UI components need it, `force` does not bypass); on an instance stub it first tries the components MOUNTED on the instance (physical removal — an emptied `cc.MountedComponentsInfo` record goes entirely, NO removedComponents entry), otherwise delegates to instances.js (removedComponents). `set_component_property`/`set_asset_ref` on a stub address mounted components the same way (`findMountedComponent`: type/script-name matching, `target: "<mount path>"` / `componentIndex` disambiguation; a no-match error lists the mounted components and points source-prefab properties to `set_instance_property`). **targetOverrides.js** implements `@property` references INTO collapsed instances: `$node`/`$component` values that resolve inside a stub serialize as `null` plus a `cc.TargetOverrideInfo` in the document registry — `source` = plain component with `sourceInfo: null` (B1 form), or, when the source component itself lives inside an instance (`set_instance_property` with a reference value), `source` = that instance's stub with `sourceInfo` = TargetInfo carrying the component's fileId (B2 form, golden scene shape); always single-hop `localID`. Overwriting the property with a plain value drops the record (a live override shadows the serialized value on load). References from an instance to PLAIN scene objects are a different mechanism — a regular `{__id__}` inside the `CCPropertyOverrideInfo` value (golden: `playerGoldStorage`). A `{"$component": {node: "Stub", type}}` value without `target` prefers a component MOUNTED on the stub and stays a plain `{__id__}` (the golden scene references mounted components that way); mounted components as reference SOURCES use the plain B1 form. **ComponentTemplates.js** holds full 3.8.7 field sets taken from real files — ~46 templates covering UI/2D, 3D rendering (incl. `cc.Terrain`: the 16-key editor shape, asset key `__asset`, no `PAIRED_FIELDS` entry because `_asset` has no serialized twin), lights (with `cc.StaticLightSettings` extras), 3D+2D physics (incl. `cc.TerrainCollider` — one own field `_terrain` over the `Collider` base, the only template whose field ORDER is inferred from sibling colliders rather than an editor-saved sample of itself, re-save check pending), audio and particles; field sets/order verified against editor-saved production projects, values are engine 3.8.7 defaults. Template placeholders: `{__ref__: i}` into extras (wired deeply — extras may reference other extras, and two keys may share one ref: `startSize`/`startSizeX` alias the same CurveRange), `{__self_node__}` (Button `_target`), `{__self_component__}` (TrailModule back-ref to its ParticleSystem). `PAIRED_FIELDS` in operations.js is keyed by the holder object's `__type__`, so getter/setter twins inside referenced module objects (`shapeType`/`_shapeType`, `numTilesX/Y`) and light `*HDR`/plain twins mirror on every write; `cc.Mask` needs a sibling `cc.Graphics` with `_fillColor` alpha 0 (companion the editor auto-adds, not extras). **Validator.js** checks referential/bidirectional invariants (errors) and conventions (warnings), including TargetOverrideInfo and MountedComponentsInfo/MountedChildrenInfo shapes (errors) and localID resolution against source prefabs (warnings, needs `{projectRoot}` option); the missing-asset warning excludes known engine builtins. `#checkTerrain` adds warnings only (the golden corpus must stay 0-error), all of the silent-invisible class: `__asset: null`, an `__asset` whose importer is not `terrain`, `_lightmapInfos` length ∉ {0, blocks} (stale bake after a resize), layers carrying a normal map while `_useNormalmap` is false / non-default roughness-metallic while `_usePBR` is false, and a `cc.TerrainCollider` next to a DYNAMIC `cc.RigidBody` (engine-unsupported, warnID 9630; `_type` defaults to DYNAMIC, so an absent field counts) — the layer checks read the binary and therefore need assetIndex + `{projectRoot}`, through `readTerrainLayout` (not the full card: `validate()` runs on every `apply_edits` batch, and `blockCount` + the layer palette is all these checks read — 15 ms instead of 62 and 66 MB less allocation on a max-size terrain). **PrefabBuilder.js** compiles a compact spec into a prefab by generating an ops batch over a skeleton document; the wrapper convention (`visual` → child node) is built in. **MetaGenerator.js** generates `.meta` files offline (`create_asset_meta` tool; also backs the builders' `createMeta` and folder metas in the build tools) — the editor trusts a brought-along meta and keeps its UUID on import, so agent-created scripts/`.mtl`/`.anim`/`.animgraph`/`.terrain`/images/audio/folders are addressable without opening the editor; `ver` values pinned to the 3.8.7 importer table (app.asar engine-extends contributions, newer editors migrate forward), image metas get full editor-shaped subMetas (ids via `nameToId`, sizes from PNG/JPEG headers, trim as full-image placeholders with `trimType: "auto"` the importer recomputes), idempotent (existing metas are never touched — no UUID churn), models (`.fbx/.glb/.gltf`) are deliberately refused: their userData derives from model content and the MCP itself needs the editor-produced `library/` artifacts. every `.meta` reaches disk through `writeMeta` → `writeFileAtomic` (temp+rename), like the assets it accompanies: a half-written meta is not lost data (an existing one is never overwritten) but it is STICKY — `resolveAssetMeta` then refuses that path forever and `create_asset_meta` reports "meta exists" instead of repairing it — and a plain `writeFileSync` also FOLLOWS a symlinked `<asset>.meta` path, which put the meta outside the project. Both entry points therefore gate on `lstat` and REFUSE a symlink at the meta path outright, link left exactly as found and nothing written — `existsSync` follows the link, so a dangling or looping one read as "absent" and got minted over, which is UUID churn plus a write through the link. Its `resolveAssetMeta(metaPath, displayPath, mint)` is the single "which UUID does this write report and keep" decision shared by `build_prefab`/`build_animgraph`/`build_terrain` — reuse an existing meta's uuid, else mint via the caller's factory, with FOUR refusals before any bytes are written: a symlink at the path, an unreadable meta (reported with its own errno — except `ENAMETOOLONG`/`ELOOP`/`ENOTDIR`, which mean no meta EXISTS and are answered as the 255-byte filename limit they are, not as "something is at that path"), an unparseable one (the parser's message is deliberately suppressed: it quotes file content, and a symlinked path could make that content anything), and one parsing without a `uuid`. **`src/utils/assetPaths.js`** is the matching single containment check (`realpathOrSelf`/`realpathTarget`/`isInsideAssets`/`resolveInAssets`) used by every tool that writes under `assets/`: both sides are canonicalized before the separator-suffixed prefix test, because `assets/ext -> /outside` passes an unresolved `startsWith` while the write follows the link, and BOTH sides are canonicalized through their closest existing ancestor (`realpathTarget`) — resolving only the side that exists made a symlinked project root with no `assets/` yet reject every legal `outputPath`. **MiniTree.js** renders compact subtrees for `apply_edits` responses.

### Animation Graph Layer

A `.animgraph` is the same flat JSON array with head `cc.animation.AnimationGraph` — `SceneDocument` serves as its plain array container (load/renumber/serialize/save apply; `root`/`resolveNode` don't), round-trip verified byte-identical on the golden Player.animgraph including the `_variables` object-map. **AnimGraphReader.js** parses the array into a semantic model (variables, per-layer states/transitions, conditions as strings) and renders the compact text summary; enum mappings (BinaryOperator `== != < <= > >=` = 0–5; VariableType float 0 / boolean 1 / trigger 2 / integer 3) are verified against the 3.8.7 engine sources. **AnimGraphBuilder.js** compiles a compact spec (`when: "Speed > 0.1"` strings, `trigger` keys) into editor-shaped objects — Entry/Exit/Any and the event-binding pairs (Motion in/out, AnimationTransition start/end) are always generated, objects are appended in canonical DFS order so `renumber()` is an identity, plus a `.meta` (`importer: "animation-graph"`). Tools: `query_animgraph` (path or UUID) and `build_animgraph`. The `cc.animation.AnimationController` template works with the `PAIRED_FIELDS` rule in operations.js: the graph reference serializes twice (`_graph` + `graph`), and every write via `set_asset_ref`/`set_component_property` mirrors both fields (deep-copied, never aliased). The controller belongs on the skeleton root inside a model — it cannot land on a collapsed instance (unpacking the model in the editor stays manual).

### Terrain Layer

A `.terrain` is a raw native binary, never a `SceneDocument`: **`src/utils/terrainBin.js`** owns ALL format knowledge (nothing above it re-derives an index formula: `vertexIndex`/`weightTexelIndex` are the exported raw offsets every grid walk above goes through — the height accessors, terrainOps' masked writes and its smooth kernel — and the one deliberately hand-indexed loop left is `set_info`'s `rebuildHeights`, which copies the overlap between the OLD and the NEW grid, so neither side of it is this terrain's) — `readTerrain` parses V1–V8 plus the `0x01010111` "empty" sentinel with the engine's own per-version field guards and the pre-V8 1/512→1/128 height migration (`null` for a foreign magic, glb.js convention; structural corruption throws with byte offsets), `writeTerrain` emits **V8 only** with `normals` count 0 and the pow-2 zero padding, round-trip verified byte-identical on the golden 131 072-byte editor save and on the 2048-byte shipped `default.terrain`. It also holds `materialize` (the sizing branches of `Terrain._buildImp`: mis-sized buffers become flat 0 m heights / `(255,0,0,0)` weights / all-`-1` layerBuffer, exactly what the engine does on load), the authoring guards `validateTerrainGeometry`/`validateTerrainCapacity` (`TERRAIN_MAX_BLOCKS` 4096, `TERRAIN_MAX_WEIGHT_TEXELS` 4096², run BEFORE any allocation so a spec cannot ask for gigabytes) plus `validateTerrainAllocation`, the strictly-allocation subset (sizing fields + both caps, format rules waived) that `materialize(data, {allowUnwritableGeometry})` drops to for ONE caller — a batch repairing an unwritable stored geometry, whose buffers must still be rebuilt without re-applying the rule the batch is replacing, `validateTerrainData` (dense-palette and range invariants, checked before every write), the palette maintenance `compactPalette`/`removeLayer` (re-index + left-pack the affected blocks' channels, weights moved along), the sampling ports `heightAt`/`exportHeights` (`Terrain.getHeightAt`/`exportHeightField`, diagonal-split kernel, NOT bilinear) and `weightAt`, `weightUsage` (ONE sweep of the weight buffer producing both shapes anyone asks for — the per-block/per-channel rows and the per-palette-slot aggregate that is exactly those rows summed, denominator counted per (block, channel) so the two agree by construction; `query_terrain`'s block table used to re-derive it with a second, independently written loop, ~80 ms of sweeping on an 8x8-block / 512 terrain and two definitions of coverage/meanWeight free to drift), plus `readTerrainInfo`/`terrainInfoFromData` cards (the latter for `dryRun`, where there is no file to re-read; it takes an opt-in `{blockUsage: true}` that keeps `weightUsage`'s per-block rows on the card — omitted by default so a memoized card does not retain `bc0*bc1` of them — which is how `query_terrain` gets its block table) with the structural warnings both read tools surface — TWO views of ONE list, because a repeating finding must be one line to a reader and one record to a filter: `warnings` is the rendered strings (one per distinct check, a repeating family aggregated) and `warningEntries` the `{kind, count, subjects, text}` data behind them, `count` EXACT while `subjects` retains at most `TERRAIN_MAX_WARNING_SUBJECTS` (16) occurrences, since the card is serialized verbatim by `get_asset_info format: "json"` and 4096 blocks of them is ~1.6 MB — the very pathology the print cap exists for, reached by asking for data instead of text. `WARNING_RENDERERS` (kind → `{keys, enums, text}`, `__proto__: null`) is the single SPELLING of each family, which is why the wording lives in terrainBin and not in the four tools that print it (`query_terrain`, `edit_terrain`, `build_terrain`, `get_asset_info` — plus `lint_assets` through `terrainWarningText`, one occurrence's message for a per-file checklist line): three tools wording one finding three ways is what a caller then has to recognize as one problem. Entries can only be minted by `terrainInfoFromData`'s own collector or by a consumer's `TerrainWarnings` (`withTerrainWarnings` folds a consumer's findings — an unresolvable layer texture is a defect IN the binary that only an AssetIndex can SEE — into a new card), branded in a `WeakSet` so a hand-built entry is refused rather than rendered; `renderTerrainWarnings(info, {own, drop, reword, limit})` is the one printer, `TERRAIN_MAX_WARNINGS` (8) the printed-line cap and `terrainWarningElision` the single elision spelling (`… and N more <noun>s (M total)`, a bare continuation line and never a bullet, so no header ever counts an elision as a problem). A `drop`/`reword` predicate sees the RETAINED occurrences and the elided remainder stays counted — dropping every retained subject of a family must not delete the occurrences past the cap with them, or a batch appending 20 layers reported 16 unassigned slots for the 20 it had just created, and `readTerrainLayout` = `readTerrain {skipPayload}` + the file read: it walks the same offsets without COPYING the four big arrays (empty, next to their counts and a `payloadSkipped` marker), for a consumer that needs only geometry + the layer palette — which the format puts LAST, behind those arrays, so it cannot be reached without walking them. Two engine functions are deliberately NOT ported verbatim because they are broken: `getWeightAt` divides metres by a TEXEL COUNT (every in-terrain point lands on texel 0) and `getMaxWeightLayerAt` numerically indexes a `Vec4` (`w[0]` is `undefined`, `w.y` tested twice, `w.w` never) — only the interpolation kernel is ported, while the metres→texel mapping and the argmax are corrected; `weightTexelAt`/`texelPosition` are the block-local mapping and its exact inverse (the engine uploads one CLAMP_TO_EDGE texture per block and samples it with block-local uv, so nothing ever crosses a block seam) and every painting path shares them. **heightmap.js** decodes the three height sources — inline metre rows, headerless 16-bit LE `.raw`, and grayscale non-interlaced 8/16-bit PNG through a zero-dependency decoder (`node:zlib` inflate + PNG unfiltering; every other colour type/bit depth/interlacing is refused with a message naming what was found) — and resamples them with the engine's `importHeightField`/`HeightField.getAt` scheme, with one deliberate addition: a source whose dimensions equal the VERTEX grid is copied 1:1 instead of resampled, reported as a note. **fsAtomic.js** (`writeFileAtomic`) is the Buffer-capable counterpart of `SceneDocument.save`'s temp+rename idiom — same directory (rename is only atomic within a filesystem), dot-prefixed `.<name>.tmp-<pid>-<random>` name so asset-db ignores it and a local same-user race cannot predict it (exclusive create, one retry on EEXIST), middle-truncated to stay inside the 255-BYTE filename limit, and fsynced before the rename so power loss cannot make the rename durable ahead of the data — the guarantee is atomicity always, durability where the filesystem supports fsync (an unsupported one is best-effort, a real I/O error still fails the write), the directory entry deliberately never. **TerrainBuilder.js** compiles a compact spec (`blockCount`/`tileSize`/`weightMapSize`/`lightMapSize`/`baseHeight`/`heightmap`/`layers`/`fillLayer`) into data + the exact bytes + notes; `resolveTextureRef` resolves a layer texture through AssetIndex or the builtin table to the `<uuid>@6c48a` texture sub-asset id the binary stores (rich list-the-alternatives error otherwise), and `checkTileSize`/`checkWeightMapSize`/`checkLightMapSize` are exported so `edit_terrain`'s `set_info` accepts exactly the same numbers. `weightMapSize` is guarded as a power of two in 4…1024: the editor's Terrain panel offers 128/256/512/1024 for the weight AND light map, while the engine constrains nothing (plain i16, no power-of-two check anywhere in `cocos/terrain/`, per-block texture NPOT-safe) — so the bound is an editor convention, and 1024 must be inside it or an editor-authored terrain could be lowered but never restored. **terrainContour.js** owns the analytics a MAINTENANCE edit needs — the case where a feature must blend into geometry that already exists, whose boundary is always an iso-contour of the height field (plateau rim, cliff foot, waterline, crater lip): `contourCrossings` (per-scan-line crossings, linearly interpolated between the straddling sample pair, plus `monotone` and the largest jump between adjacent lines — the check that catches a seam a point sample cannot see; `uniform`/`monotone` are only computed over consecutive SINGLE-crossing lines, because a line with two crossings is a lagoon, not a step; `linesWithoutCrossing` counts lines with NO crossing and `multiCrossingLines` those with several, which one "not exactly one" number cannot tell apart), `ContourDistance` (marching-squares segments bucketed into a uniform grid, so a query is the TRUE distance to the nearest segment rather than a grid-quantized one, bounded by `reach`, which no longer SIZES those buckets: the cell is `max(sampleSpacing, √(reach·sampleSpacing))` — the geometric mean that balances rings walked against segments per bucket, measured both ways — and a query walks buckets outward ring by ring, breaking once the ring's proven distance floor exceeds the best hit, so the answer is still the exact global nearest (cross-checked against a brute-force scan over 4000 points) while a wide `band` no longer degenerates into a full segment scan per texel, which is one scan PER TEXEL of every touched block; sign is NEGATIVE on the high side, so a band reads `inner: -1, outer: 2` = "from 1 m inside the high side to 2 m out on the low side" — SIGNED HORIZONTAL distances across the ground, never heights: how much height a band spans is the local slope's business, and on a 1:20 beach 2 m of ground is 0.1 m of height), `slopeStats` (gradient degrees from central differences, max + location, DISJOINT `(from, upTo]` buckets each carrying the `label` it is counted under — a band count read as the cumulative `<=N°` it looks like is off by every gentler band, and `query_terrain` prints both rows — and `maxStep` = the largest adjacent-sample height difference, i.e. the crease metric) and `sampleGrid`/`vertexSampleCount`.

A sample sitting EXACTLY on the threshold is the one case both halves of this file have to agree about, and it is the RULE rather than the edge case: heights are quantized to 1/128 m, so a round contour on a `build_terrain` field lands on vertices. `{h > T}` and `{h >= T}` have different boundaries and either can be the wanted edge — a plateau exactly at T has a rim only `>=` sees, a plain exactly at T has none but the hill standing on it has a foot only `>` sees. So `ContourDistance` marches TWICE and keeps the union (the second pass visits only cells that actually have a tie, so with none it does not run at all), and `contourCrossings` walks three states per line — below / exactly ON / above — emitting a crossing at a TRANSITION: interpolated between a straddling pair, or at whichever end of an on-threshold RUN a strictly-signed sample adjoins. A level surface therefore reports no crossing at all, which is the truth: it has no edge. The SIGN needs the same treatment, because a tie point's own height cannot say which side it is on (the plain is below the hill; the plateau is above the ramp), so every segment carries the local UPHILL direction — the gradient of the cell's bilinear field at the segment midpoint, per segment so a saddle's two branches differ — and a tie is signed by the side of the nearest segment it falls on. Without this the read and write halves disagreed about whether the contour EXISTS: `query_terrain {contourAt: 0}` reported a crossing per vertex on a flat field while `region.shape: "band"` refused the same contour outright. It re-derives nothing: heights come from terrainBin's `exportHeights`/`heightAt` ports, geometry from `terrainSize`/`vertexCounts`; the DEFAULT resolution is the region's own VERTEX grid, because a downsampled grid blurs the very edge being measured — bounded only by this module's own `CONTOUR_MAX_CELLS` (1e6), which the calling analytics in terrainOps keep, while `query_terrain` holds the same default to the 15x tighter budget an explicit `sampleCount` gets (see Tools below), since a budget attached to the ARGUMENT rather than to the WORK let the omitted number buy what the number itself is refused. **terrainOps.js** is the `operations.js` of terrain assets: eight ops (`set_info`, `set_layer`, `remove_layer`, `set_heights`, `adjust_heights`, `smooth_heights`, `paint_layer`, `set_block_layers`), all-or-nothing, `TerrainOpError`, `{op, summary, notes}` results, nothing touching the filesystem. Every region-taking op shares ONE mask (`buildMask`): `region.shape` `rect`/`ellipse`/`band` (a band is `contour ± inner/outer` intersected with the optional bounding rect), `falloff` + `profile` (`linear`/`smooth`/`cosine`), and the height ops add `clamp` (`raise-only`/`lower-only` = `max`/`min` against the existing surface, which makes an edit idempotent at its edges and preserves terrain an over-large mask reaches into). The falloff invariant is the point: the factor is 0 AT the region border and 1 exactly `falloff` metres inside it, so a transition band CANNOT be centred on the mask edge — the hand-rolled mistake that leaves half the amplitude standing where the mask stops, which is a step every time, in any axis, for any shape. The factor is applied by BLENDING in every consumer, weights included — `paint_layer` writes `current + (weight*255 - current) * t`, so a factor of 0 leaves the texel exactly as it was instead of writing 0; writing the older `weight * t * 255` erased coverage the mask merely reached, which left a bare stripe of the underlying layer wherever two strokes overlapped, and the tests missed it because painting onto a virgin `(255,0,0,0)` terrain makes set and blend agree. An ELLIPSE honours it on both axes by measuring the first-order distance to its boundary — `(1 - q) * q / |grad q|`, exact `rx - d`/`rz - d` along the axes and `(1 - q) * r` for a circle — capped at the inradius `min(rx, rz)`, the true largest inner distance: the old `(1 - q) * min(rx, rz)` stretched the ramp along the long axis by `rx/rz` (2 m of falloff spread over 12 m on a 60x10 m ellipse), and the uncapped formula is discontinuous AT the centre, which would leave a one-vertex dimple whenever `falloff` exceeds the inradius. The cap only bites where the ramp is already 1, so a too-wide falloff now yields ONE flat peak below full amplitude, reported by the existing note (`falloff 8 m is wider than the region's half-extent … peaks at 0.625`) — and 0.625 = inradius/falloff is exactly what `paint_layer`'s independently PREDICTED `min(width, depth)/2 / falloff` claims, which for an elongated ellipse the two used to disagree about. A `band` tapers across its THICKNESS only and its rectangle stays a pure clip: the rect defaults to the whole terrain, so including it in the taper faded every band to zero amplitude along the map border — a step in the middle of the edit, running the length of the band, that `edgeStep` cannot even see (the border row is covered, just with factor 0, and the row inside it has no uncovered neighbour). `set_heights` resamples a `rows`/`heightmap` source onto the vertex span the region ASKS for, computed before the grid clamp, so a region overhanging the terrain edge CROPS the source instead of squeezing all of it into the surviving part: a 32 m-wide 0..10 m ramp placed at x 16 on a 32 m terrain must end at 6.25 m at the edge (vertex-for-vertex identical to the same op on a terrain wide enough to hold the region), not at 10 — the clip is stated in a note and in the summary when it happens, the "at least 2 vertices per axis" guard measures the ASKED span too, and a span more than 4x the terrain's own vertex grid (`MAX_ASKED_VERTEX_FACTOR`) is refused rather than resampled, since an unclamped span would otherwise size an arbitrarily large resample grid. Masked height writes go through `writeMaskedHeights`, which blends the target against what is there (`current + (target - current) * t`) and MEASURES `edgeStep` — the amplitude left at a vertex on the mask boundary (a covered vertex with an in-grid neighbour that is not covered) — reporting it as a step only when it exceeds twice what the ramp itself explains (`maxDelta * tileSize / falloff`), because a falloff spread over N tiles necessarily leaves up to 1/N of the amplitude at the last covered vertex and that residue is exactly as steep as the ramp. `smooth_heights` runs its blur UNMASKED over the range and blends the result through the mask afterwards: applying the factor per iteration would compound it to `t^n`, a different and unpredictable curve. `set_info` is an exact `Terrain.rebuild` port (overlap-preserving heights/layerBuffer/weights, the diagonal-split weight resampler, and the engine's own early-out: when the GLOBAL weight-map dimensions come out unchanged — `[2,2]` at 64 → `[1,1]` at 128 — `_rebuildWeights` returns without remapping anything); a `prepare()` pass runs before the batch and materializes the "Create → Terrain" sentinel, rebuilds mis-sized buffers like the engine would, drops stored normals and compacts a sparse palette (left-packing any block that loses an assignment). Two conventions the engine itself lacks are imposed here: a texel's four channels sum to 255 (the shader is a plain weighted sum — a short sum just renders darker), and block slots stay left-packed (`getMaxLayer` derives the sampled layer count from the HIGHEST non-empty channel, so a hole below it renders as nothing). EVERY op that changes a block's channel SET maintains the sum — `remove_layer`, `paint_layer`'s auto-assignment and `set_block_layers` all run `renormalizeBlock` over the blocks they changed, zeroing a channel that lost its layer and rescaling the survivors; `set_block_layers` runs `remapBlockWeights` FIRST, because a weight belongs to its LAYER and not to its channel position (`[0,1] → [1,0]` swaps the coverage over, `[0,1] → [1]` keeps layer 1's bytes and drops layer 0's — renormalizing in place instead handed layer 0's coverage to layer 1 while the emitted note claimed the opposite): a stale byte under an empty channel darkens the block while it still blends two layers, and comes back as coverage nobody painted the moment that channel gains a layer again. `paint_layer` also MEASURES the invariant rather than asserting it, but only on the texels it wrote — a block-wide sweep would flag the editor's own `trunc(w*255)` output (thousands of texels in a real save) as our bug. `applyTerrainOperations` fails BEFORE `prepare()` when the file's own stored geometry is one the binary format cannot write back (the whole scalar half — `weightMapSize`, `tileSize`, `blockCount`, `lightMapSize` — asked of terrainBin's `validateTerrainGeometry`, so no format rule is re-derived here) — otherwise every op would run and then be discarded with "the edits produced an invalid terrain", blaming the batch for a property of the file; a batch that repairs it with a `set_info` is exempt, since that is the repair, and the exemption is decided by COMPOSING the batch's `set_info` values over the stored ones and re-asking terrainBin about the result — not by matching field names, or a `set_info {blockCount}` on a file whose `weightMapSize` is the offending value would be waved through and then die at write time, which is the outcome the guard exists to prevent (a mere restate falls out of the same test). `prepare()` then rebuilds the file's mis-sized buffers under `allowUnwritableGeometry`, because otherwise the prescribed repair was refused by the repair path itself and such a file — the ordinary "one wrong header field" corruption, since buffer sizes are DERIVED from `weightMapSize` — could never be edited or fixed at all. Tools: `query_terrain` (geometry/palette/per-block table (a file whose stored `layerBuffer` does not match `blockCount` answers `blocks: true` with a one-line "table unavailable — see Warnings, an edit_terrain batch rebuilds exactly these buffers" instead of silence inside the very section that was asked for; only `blocks: false` stays unacknowledged, being the caller's own argument)/height stats + `heightAt`/`weightAt`/`exportHeights`, all budgeted; `exportHeights` also renders `format: "map"` — the ASCII above/below-threshold grid that was the most informative artefact of the live task and had to be scripted every time — and takes `sampleCount: "vertex"` so the resolution a contour derivation needs is not hand-computed — resolved to a pair and then held to the SAME `GRID_MAX_AXIS`/`GRID_MAX_CELLS` budget as an explicit number, because the shorthand for 257 must not be accepted where 257 is refused (a whole 8x8-block terrain at vertex resolution is a ~100k-token dump), with the message naming what "vertex" came out as; `contourAt` and `slope` expose terrainContour, budgeted on both axes of the cost: the sampled grid defaults to the region's vertex resolution but is downsampled by a power-of-two stride (an exact multiple of the tile size) to the same per-axis 513 / 65 536-sample caps an explicit `sampleCount` obeys, with the report naming which of the two actually bound — stated in the report on its own line, since a coarser grid cannot show a feature narrower than its spacing, and a region around the edit buys the full resolution back; before this an 8x8-block terrain sampled 257x257 PER THRESHOLD while the identical `sampleCount: 257` was refused — and the PRINTED crossing table is strided down to 128 lines and cut off after 8 crossings per line (the elided count is stated) while the statistics still cover every line and every crossing: a dune field crossing each scan line dozens of times is what turned one `contourAt` into a 148 KB response. A stored `tileSize` of 0 makes every one of those vertex-grid defaults NaN-sized, so `exportHeights`/`contourAt`/`slope` name the FILE ("edit_terrain set_info {tileSize} rewrites the header") instead of failing as "sampleCount must be an integer …, got NaN" — an argument the caller never passed. `format: "json"` gets a CHARACTER ceiling of its own — `JSON_MAX_CHARS` 1 500 000 — because every budget above it counts grid CELLS while pretty-printing spends ~17 characters on each number: `JSON.stringify(model, null, 2)` turned a legal `exportHeights {sampleCount: [513, 127]}` into 1.80 MB against 455 KB of text, so the model is serialized by a `renderJson` that keeps numeric rows on ONE line (1.31 MB for a full-budget 256x256 grid) and a request that still exceeds the ceiling is REFUSED, naming the costliest section with its measured size, a `sampleCount` that fits and `format: "text"` — which has no ceiling. The guarantee is exactly that: a full `GRID_MAX_CELLS` grid ALONE always fits; sections stacked on top of one may not), `build_terrain` (meta resolved BEFORE the binary is written so an existing UUID survives an overwrite and a corrupt meta aborts with nothing written; an OVERWRITE renames the previous binary aside in the same directory first and moves it back on any later failure, so "Nothing was written." is true of the whole sequence and not just of the steps before the rename — only a failing move BACK leaves the old bytes under the temp name, which the report then names for a manual rename) and `edit_terrain` (`{terrainPath, ops, dryRun}`; `operations` is an alias). The two write tools render their result card through the shared **`src/tools/terrainCard.js`** (`terrainCard(info, assetIndex)`) so building a terrain and then editing nothing prints the same numbers in the same shape; `query_terrain` deliberately keeps its own far wider report (tables, per-channel coverage, sampling sections) and is not folded into it. Component-side editing rides the existing `add_component`/`set_asset_ref`/`set_component_property`, and `library/` is never written — an offline rewrite changes the mtime, the editor re-imports on next focus and the UUID comes from the untouched `.meta`. Standing hazard: never edit a `.terrain` while the editor has it open in its Terrain panel — the panel holds the whole terrain in memory and its next save overwrites the file wholesale. `build_terrain` states it (with the stale-`library/` note) in its result output, because creating an asset is a one-shot call and that report is the only thing the caller reads; `edit_terrain` states the same two standing hazards in its tool DESCRIPTION instead, paid once per session rather than repeated on every op of a multi-step sculpting run, and keeps its `## Notes`/`## Warnings (N)`/`## Next steps` for what is specific to THIS batch. That three-way split (both write tools) is deliberate: what the tool DID (sentinel materialized, stored normals dropped, `tileSize` snapped, a heightmap copied 1:1) is a NOTE, `## Warnings (N)` is reserved for problems with the file, and the count therefore excludes notes — a count over a mixed list called `## Warnings (2)` where the first line is "copied 1:1" is a number that reads as an alarm. On the read side, `PropertyExtractor` needed a narrow exception for `cc.Terrain`: it hides every `__`-prefixed key as serializer bookkeeping, so without the one-entry `#VISIBLE_DUNDER_KEYS` allowlist (`__asset`) every read tool would render a terrain component with no asset at all.

### Instance & Measurement Layer

**instances.js** implements collapsed prefab instances exactly as the editor serializes them: `instantiate_prefab` creates a stub node + `cc.PrefabInfo` (fileId = source prefab root's fileId) + `cc.PrefabInstance`, registers it in the document's instance registry, and accepts `.prefab` assets or model files (gltf-scene prefab read from `library/`); `set_instance_property`/`remove_instance_override` manage `CCPropertyOverrideInfo` objects, resolving `target` paths inside the source prefab into `TargetInfo.localID` fileIds (node PrefabInfo / component CompPrefabInfo); `remove_component` on a stub records a `cc.TargetInfo {localID: [CompPrefabInfo.fileId]}` in `cc.PrefabInstance.removedComponents` (the form the 3.8.7 engine reads in `applyRemovedComponents`; editor re-save verification pending) with dedup, cleanup of the dying component's overrides and an incoming-targetOverrides guard — `restore_instance_component` undoes it. Instance internals are never editable directly — only via overrides; multi-hop targets (inside nested instances) are not implemented. **Mounted components/children** (objects added ON TOP of an instance; golden shape: `cc.MountedComponentsInfo {targetInfo → localID: [mount-node fileId], components: [{__id__}]}`, components are regular serialized objects of THIS file with `node` → stub, `__prefab: null`, `__editorExtras__.mountedRoot` → stub; `MountedChildrenInfo.nodes` are regular `cc.Node`s with `_parent: null` — which is also why `Bounds.js` has to hop: a parent-chain walk ends at that null and every mounted child measures at the DOCUMENT origin, so `#worldMatrix` continues through the mount owner instead, `worldMatrix(stub) × the source-prefab TRS chain down to the mount node`. The reverse map is `mountOwners` in instances.js — shared, because Bounds is not the only ancestor walk: `find_scene_nodes`' `isScreenSpace` ends at the same `_parent: null`, and without the hop a mounted child of an instance under a `cc.Canvas` escaped the Canvas exclusion while still being measured in Canvas PIXELS and compared against a region in metres (Bounds caches the map per document; an unreadable source prefab falls back to the stub's own matrix, which is the instance origin rather than the world one). One missing hop gave both a false MISS where the node stands and a false HIT at (0, 0)) are readable AND editable: `mountedComponentEntries`/`mountedChildrenEntries`/`listMountedComponents`/`findMountedComponent` in instances.js provide the addressing, `inspect_node` renders them as **Mounted components / Mounted children** sections (full properties via PropertyExtractor with a `refResolver` that emits node/component addresses), `find_scene_nodes {component}` matches them, and the ordinary component ops edit/remove them (see Write Layer). Creating NEW mounted records via MCP is deliberately not implemented (editor work); editor re-save verification of mounted-component writes is pending. Reading instance internals: `inspect_node` on a stub expands the source prefab internals (read-only tree with `target` paths + the override list resolved from fileIds) plus an "Incoming scene references" section (targetOverrides pointing at this stub), and the `materials` check of `lint_assets` walks instances the same way to flag embedded-vs-project material mismatches per mesh ; its fifth check, `terrain`, is the same silent-invisible family — a layer whose detail/normal texture no longer resolves (read through AssetInspector, so `detailMapName === null` IS the finding) and a layer that blocks assign but whose weight channel is 0 in every texel, suppressed for blocks the engine draws flat (single assigned channel ⇒ the weight map is never sampled). Neither is reachable from `validate_document`, because those ids live in the binary and not in the scene's `__uuid__` graph. On the read side, **PropertyExtractor** surfaces target-overridden properties (serialized `null`) as sibling `<prop>__targetOverride` entries — additive only, so main-branch MCP clients keep working (locked by the snapshot tests in `test/tools/readSnapshots.test.js`; regenerate deliberately with `UPDATE_SNAPSHOTS=1`, diffs must be added lines/fields only). `find_scene_nodes` additionally filters by WORLD-XZ `region` (`{x, z, width, depth}` or `{center, radius}`) and prints each match's footprint — node ids ARE array indices in both readers, so a `SceneMinifier` match maps straight onto a `SceneDocument` index for measurement; a node with nothing measurable is matched by its world POSITION (`BoundsCalculator.worldPosition`), because for a placement question the position is the answer. That filter is in METRES, so UI pixels must be kept out of it two ways, or the question it exists for is answered wrongly on any scene with a Canvas: a `cc.Canvas` subtree is excluded outright (counted in a footer, since the nodes do exist) because a Canvas lays its children out in pixels — 1080 of them overlap any region asked about — and every measurement passes `skipUI`, so no 3D node inherits a pixel rect from a UI descendant either (the scene root otherwise spanned `x -7.693..1080`). The test is the Canvas and NOT the `cc.UITransform`: a UITransform parented into the 3D hierarchy (a world-space zone icon) has a real world position and only its rect is pixels, so `skipUI` handles the rect and the position still answers the placement question. `get_node_bounds {perChild: true}` is the same need one level down: one world AABB per direct child, since a merged group box cannot answer "which child stands at (4, 6)" — surveying two footprints of a real scene otherwise cost ~70 individual calls. On a collapsed instance stub the children come from the SOURCE PREFAB (`BoundsCalculator.computeChildren` → `{rows, skipped}`, marked `inPrefab` and stated in the output — a shape rather than a bare array because an unreadable source prefab makes the list INCOMPLETE and "Per child (0)" must not be indistinguishable from "no children": the reason is printed in that section (`! <path>: children NOT listed — <reason>; the count above is a lower bound`) and comes from the same `#stubSource` the merged-AABB half reports, so the two halves cannot drift apart while a comment claims they agree), because `_children` is empty there and the document view would report "Per child (0)" next to a Contributors list naming the very children whose meshes built the box. Mounted children are the other half of that list and of every merged AABB: `#enterStub` walks them at `stub frame × the source-prefab chain down to the mount node`, and `computeChildren` appends one row each, marked `mounted` (real nodes of THIS document, so NOT `inPrefab`) — a node `inspect_node` renders, `find_scene_nodes` matches and the mount hop can place must not be missing from the box that is supposed to contain it. A node with a real `_parent` is walked as that parent's child and never here: exactly one contribution per node. Neither list needs the source prefab — when it is unreadable the prefab half is skipped with its reason and the mounted children are still reported. **Bounds.js** computes subtree AABBs (mesh AABBs via AssetInspector, UITransform rects — droppable via `computeSubtree {skipUI}` for a caller measuring world ground, since the rect is in PIXELS — instance stubs through their source prefab with overrides applied, and `cc.Terrain` as an analytic box — X/Z from `blockCount*32*tileSize`, Y from the asset's height range, cached per asset uuid; that box carries `translationOnly`, so both merge loops strip everything but the translation column of the COMPOSED matrix, because the terrain shader offsets vertices by `cc_matWorld[3]` alone and honouring ancestor rotation/scale would inflate an AABB the engine never uses) in two frames: `local` (node's own frame — BoxCollider center/size) and `world`; matrix math lives in `src/utils/math3d.js`, which also holds the verified quaternion ports (`eulerToQuat` = `cc.Quat.fromEuler`, `quatToEulerYZX` = `cc.Quat.toEuler`, round-trip corpus-verified on every `_lrot` of the golden and real scenes) behind the `compute_rotation` tool — quat↔euler conversion, axis composition in world/local space (parent-chain compensation when given `filePath`+`node`; stubs read their `_lrot` override), and orient ("local axis A looks along world direction D", optional `up` roll), always answering with euler+quat+a ready-to-apply op.

Deliberately NOT implemented, after weighing it: a `fillet_heights` op ("round this corner of a contour by constructing the tangent circle"). Reshaping a contour leaves what happens to the heights OFF the contour genuinely ambiguous — the op would need a floor and a slope argument to mean anything — while the arithmetic it would hide is one formula (radius `r` tangent to two segments meeting at interior half-angle `θ` pulls the corner back by `r·(1/sin θ − 1)`, ≈ 0.2 r for a 67° turn), and the machinery it needs — contour extraction and signed distance — is now exposed as `contourAt` and `region.shape: "band"`. The formula lives in the SKILL's reshape recipe instead.

Never edit `.scene`/`.prefab`/`.animgraph`/`.terrain` files with text edits — always go through `apply_edits`/`build_prefab`/`build_animgraph`/`build_terrain`/`edit_terrain`.

### MCP Tools

Each tool extends `BaseTool` (abstract with `name`, `description`, `inputSchema`, `execute`; optional `aliases` maps courtesy argument keys onto canonical ones, e.g. `filePath`→`scenePath`). The server calls `BaseTool.run()`, which normalizes aliases and validates args against `inputSchema` (`src/tools/validateArgs.js`: unknown-key rejection with a did-you-mean hint, required/type/enum checks) before delegating to `execute()` — a bad call gets a self-explanatory error, never an internal crash like `paths[1] ... undefined`. Tools are registered in `src/tools/index.js:createTools()` and receive `projectRoot` from the server. The server (`McpServer`) uses `@modelcontextprotocol/sdk` with stdio transport.

### Key Convention: COCOS_PROJECT_ROOT

The MCP server resolves scene paths relative to `COCOS_PROJECT_ROOT` env var (falls back to `cwd()`). This is the root of the Cocos Creator project being analyzed, not this repo.

## Testing

Tests use Node.js built-in `node:test` and `node:assert`. Test fixtures live in `test/fixtures/` with a sample scene JSON, mock script `.meta` files (`test/fixtures/assets/`), and `mock-project/` — a miniature Cocos project (settings, asset metas copied from a real project, `library/` mesh + compiled gltf-scene prefab cache, generated `.glb`, prefabs for instance/bounds tests, a generated `assets/Maps/Terrain.terrain` for the terrain tests, deliberately bad-named assets for lint tests) used by asset/write-layer tests. `test/fixtures/golden/` holds unmodified editor-saved files from the real game (1.2MB scene + 4 prefabs + Player.animgraph, plus `golden/terrain/`: the 131 072-byte V8 `terrain.terrain` with its `.meta` and importer `library/` JSON, and the editor's shipped 2048-byte `default.terrain` sentinel): the write layer's round-trip tests must reproduce them byte-for-byte — for the binary that includes the pow-2 zero padding — so never reformat, hand-edit or re-save them (see `golden/terrain/README.md` for the provenance of each file). Test file structure mirrors `src/` (e.g., `test/core/SceneParser.test.js` tests `src/core/SceneParser.js`).

A real production Cocos Creator 3.8.7 3D project lives in `project-example/zombie-miner` (gitignored) — use it for manual verification of new tools against real data.

## Adding a New MCP Tool

1. Create `src/tools/NewTool.js` extending `BaseTool`
2. Implement `name`, `description`, `inputSchema` getters and `execute(args, projectRoot)`
3. Add to `createTools()` array in `src/tools/index.js`
4. Add test in `test/tools/NewTool.test.js`
